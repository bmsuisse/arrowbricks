# Performance measurements, 2026-09-06

This records the first optimization round. Subsequent download scheduling
changes and their separate baseline are measured in
[`2026-09-06-downloads.md`](2026-09-06-downloads.md).

Baseline: commit `e681224` (3.1.2). Candidate: the accompanying working-tree
changes. Both are release wheels built on the same macOS arm64 machine with
Python 3.14.3 and Rust 1.93.1. Raw measurements are in
[`2026-09-06.json`](2026-09-06.json).

## Cached IPC replay: verified improvement

Each fresh subprocess reads one IPC file and retains eight independently
replayed tables. Fixture construction happens outside the measured process.
Three process trials per version alternate order. Times below are the median
of the three per-process medians; peak RSS is the median across processes.

| Input | Replay time before | After | Peak RSS before | After |
|---|---:|---:|---:|---:|
| Synthetic: 200,000 rows, 16 Int64 columns, 26,002,184 bytes | 4.135 ms | 0.00954 ms | 253.7 MiB | 55.0 MiB |
| Real warehouse (anonymized table): 10,000 rows, 120 columns, 12,970,248 bytes | 4.321 ms | 2.941 ms | 143.1 MiB | 44.1 MiB |

The real-table replay is approximately **32% faster with 69% lower peak
process memory** in this retained-replay workload. Both versions reserialize
the entire real result to identical IPC bytes, checked by SHA-256 after
releasing the source Python bytes reference. The temporary real-data capture
was deleted after verification; no table contents or credentials are stored
in this report.

The change removes column copies by retaining immutable Python bytes through
`PyBackedBytes`, `bytes::Bytes::from_owner`, and Arrow's `StreamDecoder`.
The synthetic fixed-width case mostly becomes metadata work; the real table
still pays validation and processing costs for its richer schema. These are
**replay timings, not query/download timings**. Arrow can copy misaligned
fixed-width buffers, and supported IPC body compression requires new decoded
buffers. A retained slice can keep the entire source allocation alive.

Reproduce with dev dependencies installed and release wheels unpacked into
separate directories containing `arrowbricks/`:

```bash
PYTHONPATH=/tmp/old-wheel .venv/bin/python examples/benchmark_replay.py
PYTHONPATH=/tmp/new-wheel .venv/bin/python examples/benchmark_replay.py
```

To measure a local real IPC capture, add `--input /path/to/capture.arrow`.

## Live warehouse: no demonstrated general throughput gain

Both versions use the same actual warehouse, `protocol="thrift"`, compressed
results, concurrency explicitly set to 64, one connection per version,
one discarded warm-up each, and alternating A/B then B/A ordering. Every
query checks its expected row count. These measure `execute` plus
`fetchall_arrow`, using the same API on both sides.

| Query | Timed runs per version | Baseline median | Candidate median |
|---|---:|---:|---:|
| `range(200000)`, three columns | 6 | 0.476 s | 0.451 s |
| Real 120-column table, 10,000 rows | 6 | 0.788 s | 0.727 s |
| Real 120-column table, 500,000 rows, first run | 3 | 12.340 s | 12.557 s |
| Same 500,000-row query, repeat | 3 | 12.078 s | 12.718 s |

The large-query candidate medians are 2–5% slower here, while individual
candidate samples vary from 11.39 to 16.60 seconds. A lower peak RSS in the
first large-query run also failed to reproduce: 832→656 MiB initially,
917→957 MiB on repeat. **Neither a general warehouse speedup nor a reduction
in ordinary query peak memory is claimed.** The initial small-query run
preceded the direct-metadata scheduling change; later live runs include it.
The first large-query run overlapped some development work; its repeat ran
without other queries or builds.

An A/A control then ran **the unchanged baseline wheel in both workers**:
their medians were 14.514 s and 13.405 s, an apparent 7.6% speed difference
without a code change. Individual samples ranged from 10.391 to 16.821 s.
Peak RSS also differed (832 versus 766 MiB). This is larger than the small
A/B differences above and prevents attributing those differences to the
candidate. The raw control records retain the worker labels `baseline` and
`candidate`, but both loaded the baseline package. For further experiments,
increase `--warmups` and `--runs` and repeat this same-code control.

The direct-metadata fix has a separately verified effect: initial links can
download while the next `FetchResults` RPC is pending. Its integration test
delays that RPC for two seconds and requires the first row within one second.
It fails before the fix and passes for both supported direct-metadata
locations afterward. This helps paginated direct results; it does not promise
an improvement when all links already arrive in one response.

```bash
python examples/benchmark_versions.py \
  --baseline /tmp/old-wheel --candidate /tmp/new-wheel \
  --sql 'SELECT * FROM your_catalog.your_schema.your_table LIMIT 500000' \
  --expected-rows 500000 --concurrency 64 --runs 6
```

The script reads warehouse credentials from the environment or `.env`.
It verifies the imported package path, keeps one connection per worker,
and reports raw execute/fetch timings as well as medians.

## Package and local build cache

| Release artifact | Before | After | Reduction |
|---|---:|---:|---:|
| Wheel | 3,382,093 bytes | 3,373,919 bytes | 8,174 bytes (0.24%) |
| Compiled extension | 9,321,024 bytes | 9,288,736 bytes | 32,288 bytes (0.35%) |

These savings are modest. Most unused code was already eliminated by LTO.
The umbrella `arrow`, `arrow-arith`, `arrow-row`, and `arrow-string` crates
are removed from the dependency graph, avoiding their future build artifacts.
Only `pyo3-arrow` uses `opt-level="z"`; the IPC decoder retains its previous
optimization level. No Python runtime dependency was added.

The local Cargo target directory fell from about **5.7 GiB to 2.2 GiB** after
cleaning stale development artifacts and rebuilding with line-table-only
debug information. That includes cleanup of historical artifacts; it is not
a controlled claim that the profile alone reduces every developer's cache
by that percentage. Incremental compilation remains enabled. Full debug type
information can be restored using `CARGO_PROFILE_DEV_DEBUG=2`.

## Validation

- Rust: 115 passed, one deliberately ignored performance test.
- Python cursor suite: 65 passed, one environment-specific skip.
- Python extension suite: 47 passed.
- Installed wheel replay/write round-trip works without any optional dependencies.
- Input ownership, post-deletion lifetime, multiple batches, schema-only
  results, invalid streams, and trailing bytes are covered by replay tests.
- Existing compressed, split-download, ordering, cancellation, and error
  tests pass. The single-response download path keeps its original buffer
  while preserving assembled-length validation.
- Ruff, type checking, and Rust formatting pass. Clippy passes with the
  repository's pre-existing `type_complexity` warnings allowed.

The former connector comparison incorrectly measured RSS before imports and
queries, producing its published 16 MB figures. Those figures and their
interpretation were removed from README; the script now samples after the
workload. Its latency comparison still intentionally compares Python rows
from the connector with Arrow tables from arrowbricks, now stated explicitly.
