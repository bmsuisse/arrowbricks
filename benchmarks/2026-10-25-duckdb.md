# arrowbricks -> DuckDB 2.0.0 (vs 1.5.6)

`benchmark_duckdb.py`, local mock warehouse (SEA, loopback, no compression), no
credentials. 20 chunks x 100k rows = 2M rows, ~100 MiB of Arrow IPC on the wire;
6 columns (int64, high-cardinality string, int32, double, low-cardinality string,
timestamp). Each pipeline runs in its own process; 5 timed trials after a warmup
(11 for the reruns). arrowbricks built `--release`, same wheel for both DuckDB versions.
Query: `GROUP BY status` with count / sum(qty*price) / count(distinct sku).
Result hashes are identical across versions for every pipeline.

| pipeline | what it measures | DuckDB 2.0.0 | DuckDB 1.5.6 | peak RSS 2.0.0 / 1.5.6 |
|---|---|---|---|---|
| `arrow_zero_copy` | `fetchall_arrow` -> `register` -> aggregate | 0.29 s | 0.29 s | 462 / 467 MiB |
| `arrow_via_pyarrow` | same, with a `pyarrow.table()` conversion first | 0.25 s | 0.27 s | 456 / 460 MiB |
| `to_parquet` | fetch -> `COPY ... TO parquet` | 0.52 s | 0.51 s | 682 / 659 MiB |
| `load_table` | fetch -> `CREATE TABLE AS` -> aggregate | 0.39-0.49 s | 0.45-0.58 s | 576-592 / 656-658 MiB |
| `replayable` | cached IPC bytes via `ReplayableArrowChunk` (100k rows, no network) | 0.034-0.048 s | 0.036-0.043 s | 222 / 215-229 MiB |
| `legacy_rows` | `fetchall()` row tuples -> pyarrow -> bulk load (100k rows) | 0.49 s | 0.45 s | 252 / 269 MiB |

## Reading it

- DuckDB 2.0.0 reads arrowbricks' Arrow capsule (`__arrow_c_stream__`), including the
  two-call schema-peek-then-scan that `ReplayableArrowChunk` exists for. Nothing
  broke; answers match 1.5.6 bit for bit (after rounding the float sum).
- Speed is a wash between the two DuckDB versions except `load_table`: ~10-15% faster
  and ~10% less memory on 2.0.0, repeatable across two reruns of 11 trials.
- Registering the arrowbricks table directly versus converting through
  `pyarrow.table()` first gave the same end-to-end time (fetch + aggregate), so
  pyarrow is not needed in the middle. This does not isolate the handoff's own cost.
- Arrow vs row tuples (different workloads, so read as order of magnitude only):
  the Arrow pipeline took 0.29 s for 2M rows including the aggregate, while
  `fetchall()` + a bulk load took 0.49 s for 100k rows (it also builds a table;
  the Arrow pipeline does not). `fetchall()` itself is fast (20k rows in 77 ms);
  most of the rest is building Python objects and re-encoding them.
  `executemany` is another ~100x slower (~0.7 ms/row on 2.0.0) and is not benchmarked.
- Loopback only: this measures arrowbricks plus the DuckDB handoff, not network.
