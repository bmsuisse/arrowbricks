# 3.1.4 release validation

The retained changes passed 241 local tests against the rebuilt 3.1.4 wheel:
121 Rust, 72 Python and 48 PyO3 tests. Three manual benchmarks were ignored and
one Python test skipped. Ruff, type checking, formatting and Clippy passed.
Replay also worked with no optional Python dependencies installed. CI passed
its build, dependency-free check and Python 3.11–3.14 jobs in
[run 34062906090](https://github.com/bmsuisse/arrowbricks/actions/runs/34062906090).

The final local wheel contains exactly the same Python/native code as the wheel
used by those tests and warehouse checks. Subsequent changes are documentation
in package metadata and the SBOM timestamp/identifier. The local wheel is
3,378,064 bytes; its compiled extension is 9,288,800 bytes. Artifact hashes and
[sanitized diagnostic records](2026-09-07-release-3.1.4.json) identify this build.
Local wheel and source-archive inspections found no private warehouse material.

## Warehouse correctness: values versus IPC metadata

An initial strict IPC comparison stopped before recording any performance sample.
Deeper checks compare decoded values in memory as well as serialization. Two warm
500k-row comparisons matched all decoded values in row order, canonical schema,
batch sizes and IPC bytes. Each returned all 120 columns and 235 batches.

A separate, explicitly ordered 500k-row comparison matched all decoded values in
row order and all 218 batch sizes, but differed in schema and IPC serialization.
An ordered 500,001-row diagnostic isolated the schema differences to field
metadata on all 120 columns: names, types, nullability and schema-level metadata
matched. No names or metadata contents were logged.

Crucially, an identical-code control reproduced this metadata-only difference:
both workers used the unchanged released 3.1.3 build, queried the same snapshot
with explicit ordering, and returned 500,002 rows in the same 218 batch sizes.
This proves that strict IPC differences can occur without the new optimizations.
The control examined schema and serialization, not decoded-value hashes.

The existing implementation selects submission/direct-result schema when it is
available, otherwise the first decoded cloud-file schema. Review confirmed that
reordering prevents fetch completion order from selecting a later chunk's schema.
The observed cold/warm metadata difference is consistent with those pre-existing
schema sources; these changes do not normalize or discard caller-visible metadata.
The initial failed pair was not retained for deeper inspection, so its exact
contents cannot be reconstructed from that run alone.

A fixed snapshot alone does not make an unordered LIMIT query deterministic.
Databricks documents using [ORDER BY with LIMIT](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-qry-select-limit)
for deterministic results. Strict `--verify-ipc` additionally requires stable
schema metadata and batch boundaries; differing IPC is not, by itself, proof of
differing decoded values. The final ordered value check preserves that distinction.

These diagnostics are correctness evidence, not additional speed claims: cold
execution, sorting, changed snapshot/chunk shapes and lengthy untimed validation
make their timings unsuitable for combining with the controlled benchmarks.
The repeated speed measurements and memory tradeoffs remain in the
[spare-slot report](2026-09-06-spare-slots.md) and
[IPC/NDJSON report](2026-09-06-lowlevel.md).

All queries were read-only. Data, schema metadata and comparison hashes stayed
in process memory/private pipes. Public records contain only counts, timings,
equality flags and compiled-artifact hashes.
